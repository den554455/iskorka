# Отчёт: логирование, привязка к user_id, ударения

## 1. Что было в исходном коде
- Логирование: только `logging.basicConfig(level)`; request id, времени обработки и маскирования не было. Команда Amvera запускает uvicorn с access-логом, в котором виден путь `/alice/<секрет>`.
- Идентификация: `application_id` (запасной вариант — устаревшее `session.user_id`), ключ профиля `HMAC(pepper, "alice:"+id)`. `session.user.user_id` схема читала, но не использовала.
- БД: SQLite, ручные миграции в `Database._migrate`, Alembic нет.
- **Найден дефект транзакций:** pysqlite при `begin_nested()` (SAVEPOINT) фиксировал внешнюю транзакцию, поэтому откат хода не откатывал привязку профиля. Исправлено рецептом SQLAlchemy для pysqlite (`app/db/database.py`).
- `_STRESS` — 4 правила, добавлены в предыдущей итерации без прослушивания.

## 3. Миграция БД
`profiles.user_key VARCHAR(64) NULL` + `CREATE UNIQUE INDEX ux_profiles_user_key` (в `Database._migrate`, идемпотентна). Строки не пересоздаются; существующие профили получают `user_key = NULL` (анонимные). Проверено тестом на старой схеме: данные сохраняются, повторный запуск безопасен.

## 4. Перенос профиля
Авторизованным считается только `session.user.user_id`. Порядок:
1. есть профиль с таким `user_key` → используется он;
2. иначе анонимный профиль этого приложения, не привязанный ни к кому, получает `user_key` (прогресс, решения, награды, знакомства, пройденные эпизоды остаются на месте — копирования нет);
3. иначе создаётся новый профиль пользователя.
**Конфликт:** у пользователя есть профиль, на устройстве другой анонимный → используется профиль пользователя, анонимный не изменяется и не удаляется (в журнале «Конфликт профилей»). Анонимный профиль, уже привязанный к другому пользователю, не переносится: второй пользователь получает новый профиль. Прогресс не объединяется. Операция идемпотентна; от гонок защищают замок сервиса и UNIQUE по `user_key`; откат хода откатывает и привязку.
Особенность: после привязки неавторизованный запрос с того же устройства продолжит тот же профиль (ключ приложения сохранён).

## 9. Остающиеся риски
- Реальная структура запроса с `session.user` проверена по документации и тестам, не на живом навыке.
- Привязка необратима без ручной правки БД (`user_key` можно обнулить SQL-запросом).
- Несколько процессов/реплик: межпроцессная гонка закрыта UNIQUE и повтором выборки, но замок сервиса — внутрипроцессный.
- Дублирование: у запроса две строки (наша и access-лог Uvicorn) — осознанно, чтобы не отключать штатные сообщения.
- Ударения и паузы на слух не проверены.
